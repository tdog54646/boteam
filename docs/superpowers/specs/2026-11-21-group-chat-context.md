# BoTeam 群聊共享上下文与消息引用

2026-11-21 · 产品与实现规格 · 已评审

## 用户应当能做到什么

用户在项目群中让 Codex 给出方案，等它答完，再第一次点名 Claude Code 或 Antigravity 评审其中一点。后发言的成员知道用户问过什么、谁给了什么方案。即使该成员的原生会话后来发生压缩，用户也能通过「引用」让它重新看到指定消息的原文。

当前界面已按群展示消息，发送路径只将本条正文和本次附件交给被选中的成员。本规格修订原设计中「新成员只接收自己被分配的任务和本群内自己的原生上下文」的约定。群记录决定成员发言时可读的公开内容，点名和接收人选择决定本轮谁执行任务。[原工作台规格](2026-11-20-boteam-design.md) · [原输入框规格](2026-11-20-composer.md)

## 发言与引用

- 用户可通过文字点名、接收人面板或 `@全体` 派活。只唤醒本轮选中的成员。用户要听取独立意见时，多位成员并行读取同一时刻的群记录；用户要接力评审时，等前一位答完再点名下一位。首版由用户发起每一轮。
- 本群含公开正文的用户消息和成员已经完成的公开文字回复提供「引用」操作，鼠标悬停或键盘聚焦均可找到。选中后输入框显示原作者、截短预览和移除按钮。一条新消息可引用一条原消息，再次选择可替换引用。用户照常输入问题并选择接收人。引用作者可以与接收人不同，预览里的 `@` 也不会触发点名。
- 派活入队后，新消息展示可点击的引用预览，点击回到群中原消息。使用消息 ID 建立关系，用户无需看到或输入序号。入队前校验失败时保留问题与引用。引用与正文共用原群草稿，在本次打开应用期间切群可恢复，入队成功后清空。仅选中引用时可以暂存，发送仍需接收人和有效任务内容。
- 普通追问仍可直接发送。近期群记录为“刚才的第二点”提供上下文；若要让成员读到某段确切原话，用户可以主动引用。界面不需要用户知道某个原生会话是否压缩过。

## 一轮对话怎样进入原生工具

1. **发送时确定范围。** 桌面主进程校验当前群、接收人和引用目标，将用户消息、引用关系和各成员任务一并写入 SQLite，并固定本轮可读的最后一个发布序号。即使某位成员排队较久，BoTeam 也只补入本次提问时已发布的群记录。这个边界约束 BoTeam 附加的文字；同一成员的原生线程仍会记住先执行的任务及其答复。
2. **轮到成员时组装输入。** 按「群、成员、实际原生线程」读取上次成功送达的位置，从本轮范围中取出尚需补充的公开消息，按发布顺序标明发言人和原点名对象。首次参与或更换原生线程时，按历史预算补入既有记录。历史、明确引用的原文、用户当前请求在同一条输入中分段；同一消息在本次输入中只出现一次，当前请求放在最后。
3. **沿用原生普通对话入口。** Claude Code 使用 `--session-id` 或 `--resume` 后发送 stream-json 用户消息。Codex 在新建或恢复的线程上调用 `turn/start`。Antigravity 通过 `agy acp` 新建或恢复会话，再调用 `session/prompt`。三者沿用成员自己的订阅、模型、目录与工具权限。补发群记录无需单独启动旁听成员或请求模型先阅读一次。
4. **完成后发布。** 成员的完整公开回复写入群记录，归属实际发言的 bot。后续被点名的其他成员可以读到它。成员自己的当前请求和成功生成的回复已进入其原生线程，后续普通补发时可按消息 ID 去重。

| 会进入共享历史 | 按成员处理的内容 |
| --- | --- |
| 本群普通用户消息的公开正文、作者及原接收人，成员已完成的公开文字回复，消息的引用关系 | 私聊和其他群记录，原生压缩内容、工具日志、审批、身份与配额信息 |
| 用户或 bot 主动写进公开正文的文件名、路径、结论或说明 | 附件快照、图片数据、系统附加的本机快照路径、扩展选择与授权按当前派活投递。引用消息只取公开正文，其他成员需要文件时可在新消息里附上 |

原生控制操作使用各自的协议。调用 `/compact` 压缩选定成员的线程；无参数的 Codex `/review` 沿用对工作区改动的审查，目标操作沿用结构化目标。此类操作单独执行，不接受群引用、不拼接历史，也不推进普通群消息的送达位置。命令参数、目标状态和控制回执属于成员任务详情。作为公开答复展示的 `/review` 最终审查正文可以引用、可以供后来成员阅读。用户要评审群里的文字方案，可用普通消息引用方案并点名成员。

## 原生压缩之后

原生工具决定当前线程如何压缩。此前送给它的群发言也属于其上下文，压缩后可能只剩大意。原生压缩结果归该线程内部使用；群中仍保存源消息、原作者和完整公开正文。BoTeam 的送达位置用来减少重复输入，不能证明模型仍记得原文。

**明确引用始终回到群消息取原文。** 主进程根据引用 ID 校验目标与当前消息同群、内容已发布，再从 SQLite 取作者和正文。即使目标早于送达位置、落在历史预算外，或该工具没有报告自动压缩，也按相同规则处理。若目标也在本轮普通历史中，保留引用段的完整版本。引用跨群、失效或只剩未完成回复时，入队前提示用户重新选择，保留草稿。

例如，Codex 在群里说“错误率连续 5 分钟超过 2% 时回滚”。Claude 已评审过，随后其原生会话压缩。用户引用 Codex 的原话，点名 Claude 说“把阈值改成 1%，其余照旧”。BoTeam 恢复 Claude 的原生线程并随这次普通输入送入以下两段：

> **引用 · Codex**　错误率连续 5 分钟超过 2% 时回滚。
>
> **当前请求 · 用户 → Claude**　把阈值改成 1%，其余照旧。

Claude 本轮有据可答“连续 5 分钟超过 1% 时回滚”。群里新增一条由 Claude 发布的回复；原生压缩没有产生任何群成员发言。

## 长群聊的输入预算

当前请求和明确引用优先，其次是最近的完整群消息。首版建议把**自动附带的历史**限制在约 8,000 个估算 token，有可靠的模型窗口读数时取该窗口的 10% 与 8,000 中较小者。该预算用于控制 BoTeam 附加的输入量，原生工具仍自行管理整个线程的窗口。

超出预算时，优先保留最近原文，另为早期消息留出少量带作者的摘录空间。标出省略范围，所有原文仍可在群里引用。首版建议采用本地摘录，不额外消耗某位成员的订阅生成群摘要。明确引用可以占用普通历史的额度并优先完整投递。如果仅当前请求和明确引用就超出某个成员可接收的输入，在该成员任务上说明原因，其他成员照常执行。原问题与引用保留在已发送消息中，用户可缩短请求或直接粘贴所需片段后重新点名。

## 发布顺序、重启与旧群

- 群内每一条可共享的消息有稳定 ID 和单调递增的发布序号。用户消息在提交时发布，bot 回复在任务成功、最终正文落库时发布。回复占位和流式片段仍可供用户查看，成为其他成员的上下文须等到正式发布。取消、失败和中断留下的片段不参与自动补发或引用。
- 引用关系建议用可空的 `replyToMessageId` 保存。发布最终正文、任务成功状态与发布序号应原子提交，重复的完成通知只发布一次。并行任务读取相同范围，但各自的补发量可以不同。A 先创建占位、晚于 B 的提问才完成时，A 的答复留给下一次提问。
- 同一群内同一成员按派活顺序执行。普通任务成功后，将该原生线程的送达位置单调推进到本轮**已处理的快照边界**。因预算被摘录或省略的消息同样越过，此后用户可以引用原文。任务期间可能有其他成员发言，不能把自己刚生成的回复序号直接当成送达位置。
- 失败或中断保留上一次成功位置，也不自动重发。用户再次发送按新一轮派活，取新的发布边界，不回退原生线程。上次投递结果不确定时允许重送带同一 ID 的背景消息。重启恢复送达位置与原生线程关联；替换线程时重新补入有预算的群历史。
- 升级时给旧群的普通用户正文和已成功完成的公开文字回复补发布序号，按原有群记录展示顺序建立一次性基线。用旧任务的命令、目标及完成状态识别控制回执；无法可靠区分的旧任务记录仅保留原界面展示。旧库缺少回复完成时刻，后续新消息才按实际发布时间追加。旧消息初始无引用，既有线程首次按历史预算同步，不重跑旧任务。建议新加入的成员可在首次被点名时读取加入前的本群公开历史。

## 验收

| 场景 | 可观察的通过条件 |
| --- | --- |
| 跨工具接话 | Codex 发出两个自带唯一标记的方案，重启 BoTeam 后首次点名另一成员评审第二项。实际送入该成员的输入含第二项原文和 Codex 的作者标记；旁听成员无任务。Claude Code、Codex、Antigravity 均作为接收方覆盖。 |
| 压缩后引用 | 确认接收方已收到带时长和阈值的旧消息，对其线程执行原生压缩并重启。通过「引用」追问，恢复同一线程，普通输入再次包含完整原文及本次问题。即使测试替身把数字从压缩上下文中移除，也可从本轮输入准确作答。 |
| 引用交互 | 鼠标和键盘均能引用、替换、移除，发出后可跳回原文。引用 A 并点名 B 只产生 B 的任务。跨群 ID、流式占位和失败片段不能作为来源。 |
| 并行与排队 | 同轮 `@全体` 固定相同的发布边界。让 A 在 B 派活后才完成，即使 A 的占位更早创建，B 本轮也不会收到半截回复，下一次派活能补到 A 的完整发言。 |
| 隔离与原生命令 | 群 A、群 B 和私聊各放不同标记，普通群输入只出现本群公开标记。历史附件内容、工具日志和审批细节不会随引用转发。无参数 `/review`、`/compact`、目标命令沿用原生参数。 |
| 旧群、失败与预算 | 升级旧库后能引用一条旧回复。取消任务、重启及手动重试均无漏发的迟到回复或重复发布。长群首次点名遵守历史预算，明确引用在预算紧张时仍得到完整投递或明确提示。 |

适配器协议测试检查实际送出的文本与任务次数，桌面验收检查用户交互。真实订阅验收分别记录工具版本、账号可用性、是否经过原生压缩及模型回答；已有的独立线程续聊记录不代表跨成员共享已通过。性能对照使用同一工具和模型，分别测连续追问、首次进入长群时的输入 token 和首字延迟。[已有验收记录](../../acceptance.md)

## 取舍与参考

逐轮重发全量群记录实现简单，长群的重复输入会增长。每群每成员复用原生线程、在被点名时补充公开历史，可以沿用三种工具的执行和账号边界。自动轮流讨论会改变现有多人并行派活的体验，建议在有明确接力需求时单独设计。[Codync 群会话](https://github.com/leepokai/Codync/blob/876492dbcd250d11cb4fcafe861730bf3d22186f/docs/features/groups-and-replies.md#L59-L81) · [multiagent 的并行与顺序模式](https://github.com/matheusvanzan/multiagent#-features)
